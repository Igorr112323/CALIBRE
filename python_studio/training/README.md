# Исследовательское обучение Kolibri Qwen2.5-3B

**Improved using Qwen.** Базовая модель `Qwen/Qwen2.5-3B-Instruct` распространяется по [Qwen Research License](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/blob/main/LICENSE). Стандартная лицензия ограничена некоммерческими исследованиями и оценкой; для коммерческого использования необходима отдельная лицензия. При публикации workflow прикладывает исходный текст лицензии и `NOTICE.txt`, описывающий изменение модели.

## Данные

`build_dataset.py` принимает только проверенные по SHA-256 копии `examples/РуководствоПоГраблям.pdf` и `examples/sample-catalog.json`. Он сверяет каждое наименование, отдельное обозначение, количество и примечание всех 124 позиций по соответствующей строке таблицы PDF; для 79 подготовленных фактов проверяет наличие цитируемой выдержки на указанной странице. Затем формирует 348 примеров: 124 о деталях, 158 вопросов о фактах РЭ и 66 примеров правок, безопасных отказов и обработки попыток внедрения инструкций. Синтетические запросы на изменение значений не являются заводскими нормами. Поля `purpose` и `inspection` эталонного каталога не используются как подтверждённые факты.

```text
python python_studio/training/build_dataset.py
```

Результат — `train.jsonl` с сообщениями и ссылками на источники, а также `dataset-manifest.json` с контрольными суммами. Генерация детерминирована и не изменяет пользовательский каталог. Контексты для обучения сокращены, а оригинальный системный промпт Studio сохранён. Дополнительные правила, которые студия добавляет в реальных запросах, не включены в тренировочный промпт, потому что вместе с ними примеры не помещаются в 448 токенов. Это отличие обучения от реального режима может ухудшить результаты. Ответ, входной JSON и системное сообщение не обрезаются: слишком длинный пример вызывает ошибку обучения.

## Запуск

Workflow `.github/workflows/train-kolibri-gguf.yml` запускается при изменении обучения в ветке `arena/0d487d0e-calibre` или вручную, когда GitHub разрешает запуск workflow из выбранной ветки. Для ручного `workflow_dispatch` GitHub обычно требует, чтобы этот workflow уже существовал в ветке по умолчанию. Выполнение требует доступа к Hugging Face и CPU runner Ubuntu 24.04; включается файл подкачки 8 ГБ. Веса и промежуточные файлы не коммитятся.

Для самостоятельного запуска необходим Python 3.11, CPU-сборка PyTorch 2.6.0 и зависимости `requirements-training.txt`. Обучение и конвертация — отдельные процессы:

```text
python python_studio/training/build_dataset.py
python python_studio/training/train_kolibri_gguf.py --threads 4 --max-length 448 --target-minutes 32 --output /path/to/work
python python_studio/training/train_kolibri_gguf.py --convert-only --output /path/to/work --llama-source /path/to/llama.cpp --quantize /path/to/llama-quantize --threads 4
```

По умолчанию используются веса Qwen2.5-3B-Instruct ревизии `aa8e72537993ba99e69dfaafa59ed015b17504d1`, BF16 на CPU и LoRA r16/alpha32 в проекциях `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj` слоёв 24–35 из 36. Последовательности имеют реальную длину без дополнения до общего размера; loss вычисляется только по токенам ответа. Первые три шага измеряются, выводятся время шага и приблизительная длительность одного прохода. Скрипт старается уложиться в заданное время, но обязательно выполняет полный проход по данным; при медленном CPU 25–40 минут не гарантируются. При достаточно быстром CPU допускается до двух проходов. `--max-steps` предназначен для неполной проверки механики; такой результат не пройдёт выпускной контроль.

До и после обучения измеряется loss на одной и той же небольшой подвыборке обучающих примеров. Это контроль изменения весов, а не независимая валидация качества. Сохраняются реальные скорости, loss, число увиденных примеров, параметры LoRA и SHA-256 датасета. Затем адаптер объединяется с базовой моделью и конвертируется закреплённым llama.cpp `b7571`, после чего используется именно `Q4_K_M`.

## Экзамен и ограничения публикации

`evaluate_finetuned.py` вызывает без изменения `tests/evaluate_real_model.py` со всеми семью исходными сценариями и добавляет пять проверок устройства, отсутствующих сведений и сохранения безопасности. Сервер проверяется по имени, вычисляется SHA-256 GGUF. В Actions сервер запускается с явным путём к построенному файлу; само API сервера не является криптографическим доказательством происхождения модели. Отчёт содержит фактические ответы и изменения на копии примера. Короткий локальный smoke экзаменатора на другой модели не означает, что экзамен 3B выполнен.

`verify_release.py` запрещает публикацию, если не совпадают исходные веса и архитектура, не пройден полный датасет, не изменился адаптер или не снизился диагностический loss; если отсутствует любой сценарий, не прошли все эвристики, не совпадает SHA-256 или файл имеет размер **1 950 000 000 байт и более**. Ошибки и реальные результаты, если они были получены, сохраняются в artifact `kolibri-qwen-training-diagnostics`. Release с тегом `kolibri-ai-model` создаётся как черновик и становится публичным только после прохождения проверок; существующий релиз скрипт не перезаписывает.

Официальная базовая Qwen2.5-3B Q4_K_M занимает 2 104 932 768 байт. LoRA не уменьшает размерность модели, поэтому заданный предельный размер может оказаться недостижимым без изменения формата или архитектуры. Workflow не подменяет модель и не публикует файл сверх лимита. Ни успешное снижение loss, ни все эвристики не гарантируют точность или безопасность: производственное применение требует ручной проверки по РЭ. При отсутствии релиза первый профиль студии честно сообщает, что модель ещё не опубликована.
