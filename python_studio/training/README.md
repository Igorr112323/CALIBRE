# Исследовательское обучение Kolibri Qwen2.5-3B

**Improved using Qwen.** Базовая модель `Qwen/Qwen2.5-3B-Instruct` распространяется по [Qwen Research License](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/blob/main/LICENSE). Стандартная лицензия ограничена некоммерческими исследованиями и оценкой; для коммерческого использования необходима отдельная лицензия. При публикации workflow прикладывает исходный текст лицензии и `NOTICE.txt`, описывающий изменение модели.

## Данные

`build_dataset.py` принимает только проверенные по SHA-256 копии `examples/РуководствоПоГраблям.pdf` и `examples/sample-catalog.json`. Он сверяет наименование, обозначение, количество и примечание всех 124 позиций по соответствующим строкам таблиц PDF; для 79 подготовленных фактов проверяет наличие выдержки на указанной странице. Генерируются 348 примеров: 124 о деталях, 118 вопросов по фактам РЭ, 20 объяснений, 20 перефразирований, 24 числовые правки, 12 добавлений шагов и 30 безопасных отказов или проверок инструкций в источнике.

Перефразирования вручную сверены с исходными фактами. В примерах числовых правок и старое, и новое число встречаются в РЭ, но замена явно представлена как запрос пользователя и не становится заводской нормой для изменённого параметра. Добавления и запросы на правку — синтетические учебные действия, а не дополнительные утверждения изготовителя. Поля `purpose` и `inspection` эталонного каталога не используются как подтверждённые факты.

```text
python python_studio/training/build_dataset.py
```

Результат — `train.jsonl` с сообщениями и ссылками на источники, а также `dataset-manifest.json` с контрольными суммами. Генерация детерминирована и не изменяет пользовательский каталог. Категории примеров распределяются по проходу, а не группируются в конце. Контексты для обучения сокращены, исходный системный промпт Studio сохранён. Дополнительные правила, которые студия добавляет в реальных запросах, не включены в учебный промпт, потому что вместе с ними примеры не помещаются в 448 токенов. Это отличие обучения от реального режима может ухудшить результаты. Ответ, входной JSON и системное сообщение не обрезаются: слишком длинный пример вызывает ошибку обучения.

## Запуск

Workflow `.github/workflows/train-kolibri-gguf.yml` запускается при изменении обучения в ветке `arena/0d487d0e-calibre` или вручную, когда GitHub разрешает запуск workflow из выбранной ветки. Для ручного `workflow_dispatch` GitHub обычно требует, чтобы этот workflow уже существовал в ветке по умолчанию. Выполнение требует доступа к Hugging Face и CPU runner Ubuntu 24.04; включается файл подкачки 8 ГБ. Веса и промежуточные файлы не коммитятся.

Для самостоятельного запуска необходим Python 3.11, CPU-сборка PyTorch 2.6.0 и зависимости `requirements-training.txt`. Обучение и конвертация — отдельные процессы:

```text
python python_studio/training/build_dataset.py
python python_studio/training/train_kolibri_gguf.py --threads 4 --max-length 448 --target-minutes 32 --output /path/to/work
python python_studio/training/train_kolibri_gguf.py --convert-only --output /path/to/work --llama-source /path/to/llama.cpp --quantize /path/to/llama-quantize --quantization Q3_K_M --threads 4
```

По умолчанию используются веса Qwen2.5-3B-Instruct ревизии `aa8e72537993ba99e69dfaafa59ed015b17504d1`, BF16 на CPU, learning rate `0.0001` и LoRA r16/alpha32 в проекциях `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj` слоёв 24–35 из 36. Последовательности имеют реальную длину без дополнения до общего размера; loss вычисляется только по токенам ответа. Первые три шага измеряются, выводятся время шага и приблизительная длительность одного прохода. Скрипт старается уложиться в заданное время, но обязательно выполняет полный проход по данным; при медленном CPU 25–40 минут не гарантируются. При достаточно быстром CPU допускается до двух проходов. `--max-steps` предназначен для неполной проверки механики; такой результат не пройдёт выпускной контроль.

До и после обучения измеряется loss на одной и той же небольшой подвыборке обучающих примеров. Это контроль изменения весов, а не независимая валидация качества. Сохраняются реальные скорости, последний loss, число увиденных примеров, параметры LoRA и SHA-256 датасета. Затем адаптер объединяется с базовой моделью и конвертируется закреплённым llama.cpp `b7571`. Основной формат — `Q3_K_M`; workflow также пытается отдельно построить и проверить `Q4_K_S` из того же BF16 GGUF. Ошибка построения необязательного альтернативного варианта не отменяет возможность выпуска основного.

## Экзамен и ограничения публикации

`evaluate_candidates.py` по очереди запускает `llama-server` с конкретным файлом каждого доступного варианта. `evaluate_finetuned.py` вызывает без изменения `tests/evaluate_real_model.py` со всеми семью исходными сценариями и добавляет пять проверок устройства, отсутствующих сведений и сохранения безопасности. Сервер проверяется по имени, вычисляется SHA-256 GGUF. Сам API сервера не является криптографическим доказательством происхождения модели. Отчёт содержит фактические ответы и изменения на копии примера. Локальный smoke на маленькой модели не является экзаменом дообученной 3B.

`verify_release.py` запрещает публикацию, если не совпадают исходные веса и архитектура, не пройден полный датасет, не изменился адаптер или не снизился диагностический loss; если отсутствует любой сценарий, не прошли все эвристики, не совпадает SHA-256 или файл имеет размер **1 950 000 000 байт и более**. Целевой размер Q3 менее 1 700 000 000 байт желателен, но отдельным обязательным воротом не является. Из прошедших все проверки вариантов выбирается лучший по числу успешных сценариев; при равенстве предпочтителен Q3_K_M. Если ни один вариант не прошёл, публикации нет.

`release-gate.json` печатается и сохраняется с размерами, loss, причинами отказа и результатами каждого сценария для каждого кандидата, в том числе при отсутствии части входных файлов. Подробные ответы и диагностика сохраняются как artifact `kolibri-qwen-training-diagnostics`, если состояние задания позволяет его загрузить. При подготовке выпуска повторно сверяются размер и SHA-256 модели, отчёта и метрик с проверенными воротами; перед публикацией проверяется `SHA256SUMS.txt`. Release с тегом `kolibri-ai-model` создаётся как черновик и становится публичным только после прохождения проверок; существующий релиз скрипт не перезаписывает.

Run [43511938080](https://github.com/Igorr112323/CALIBRE/actions/runs/43511938080) построил Q4_K_M размером 1 929 903 008 байт и прошёл размерный предел, но провалил экзамен: 1/7 исходных и 2/5 дополнительных сценариев. Восстановленные JSON находятся в `diagnostics/run-43511938080.json`.

Следующий run [43567132776](https://github.com/Igorr112323/CALIBRE/actions/runs/43567132776) построил Q3_K_M размером 1 590 475 680 байт и Q4_K_S размером 1 834 384 288 байт. Оба меньше обязательного предела, а Q3 также меньше цели 1,7 ГБ. Однако Q3 прошёл 0/7 исходных и 0/5 дополнительных сценариев, Q4 — 1/7 и 3/5; выпуск заблокирован. Например, Q4 выдал выдуманное значение момента затяжки, а Q3 предлагал правки, когда их не просили. Точные ответы, размеры, loss и причины сохранены в `diagnostics/run-43567132776.json`; ошибочные ответы в этом файле — диагностика, а не сведения из РЭ и не обучающие данные.

Ни успешное снижение loss, ни все эвристики не гарантируют точность или безопасность: производственное применение требует ручной проверки по РЭ. При отсутствии релиза первый профиль студии честно сообщает, что модель ещё не опубликована.
